Kernel-level enforcement for AI agents

OpenShell is a sandbox runtime platform that gives AI coding agents kernel-backed isolation. A Gateway (control plane) manages lifecycle, credentials and policy from outside the sandbox; a Supervisor (data plane) runs inside it and enforces four policy domains — filesystem, process, network and inference routing. The agent is not asked to behave: the kernel denies the syscall.

// The thesis — Layer 0 of the AIDR architecture:
Other layers govern what an agent SHOULD do. OpenShell makes “you CAN'T” real at the OS level — mathematically verified before deployment, enforced by the kernel at runtime.

01

The three-tier trust model

D0003

Tap a tier to inspect what lives there, what it can do, and what it must never hold. The Supervisor initiates an outbound-only bidirectional gRPC stream to the Gateway (ConnectSupervisor) — the Gateway never connects inward, so sandboxes work behind NAT and firewalls, and a compromised sandbox cannot pivot into the control plane.

▼ creates container / VM · outbound gRPC only · never connects inward ▼
▼ spawns as child · uid=sandbox, gid=sandbox · never root ▼
Reconciliation — “trusted Supervisor” vs “semi-trusted Supervisor”

NVIDIA's blog and docs describe the Supervisor as the trusted side, paired with each sandbox and running outside the agent workload. D0003 refines this into three tiers: the Supervisor runs inside the sandbox boundary as PID 1, so it is semi-trusted — privileged relative to the agent, but not equivalent to the Gateway outside. This page uses the D0003 three-tier model and flags the difference rather than merging the two framings.

What is confirmed at platform level NVIDIA official Docs verified

OpenShell is open source under Apache 2.0. The 2026-09-28 launch materials cite version 0.1.0; docs checked on 2026-10-29 already read v0.1.6 — cite versions with a check date. The official platform FAQ lists Claude Code, Codex, OpenCode, GitHub Copilot CLI and OpenClaw as supported agents; Cursor appears in the 2026-09-28 press release in the SpaceXAI context, not in the FAQ support list, and is not presented here as out-of-the-box support.

Eight responsibilities

1 · Sandbox lifecycle

Create, get, list, delete and watch sandboxes across all compute backends, through the ComputeDriver contract (Section 8).

2 · Credential management

Stores provider credentials gateway-side; at sandbox creation the supervisor receives the real values into its own memory only, while the agent environment receives placeholders (openshell:resolve:env:KEY). Rotation runs via OAuth2 / Google SA JWT strategies (Sections 8–9); substitution happens at egress (§5, §17).

3 · Policy management

Stores, composes (base + provider layers + drafts) and distributes policies to supervisors; network policy hot-reloads into running sandboxes.

4 · Authentication

OIDC, Kubernetes ServiceAccount, Cloudflare JWT, gateway-minted sandbox JWT, plus mTLS and SPIFFE workload identity (Section 9).

5 · Supervisor sessions

Maintains the bidirectional ConnectSupervisor stream per sandbox; if the supervisor disconnects, the agent is frozen and only the same supervisor process can reconnect and resume it.

6 · SSH sessions

Issues and revokes SSH sessions; SSH, exec and TCP traffic all relay over the single outbound supervisor stream — there is no inbound path to relay through.

7 · Service exposure

Exposes selected sandbox services externally (ExposeService / GetService / ListServices / DeleteService), under Gateway control rather than sandbox self-publication.

8 · Draft policy learning

Accepts policy analysis from supervisors, builds draft recommendations from aggregated denials, and presents them for operator approve / reject / edit / undo (Section 6).

“The agent cannot approve its own policy change” — with one opt-in exception NVIDIA official

By default, draft proposals stay pending human review and the agent cannot approve its own request. NVIDIA's docs also describe an opt-in auto-approval mode: a proposal may be auto-approved only when the prover delta is empty and there are no security notes. State the guarantee precisely — “manual by default; auto mode remains gated by prover + security notes” — not as an unconditional promise.

Supervisor deep dive

D0003 · openshell-sandbox

The enforcement engine inside the sandbox. It runs as PID 1 (init), spawns the agent as a child process, and makes every policy decision the agent cannot override. The sandbox itself makes no policy decisions of its own — enforcement semantics live here and in the Gateway.

Privilege sequence & supervisor hardening Code evidence

The agent spawn path (spawn_impl, pre_exec, in order) is where “capability removal” actually happens — there is no capset call anywhere in the supervisor:

# process.rs spawn_impl → pre_exec (code evidence, commit f23c2c8)
1. setpgid
2. setns(netns)                      # join the sandbox network namespace
3. supervisor-identity mount-ns shadow
4. drop_privileges                   # initgroups/setgid/setuid; then verify setuid(0) FAILS
5. harden_child_process              # RLIMIT_CORE=0, PR_SET_DUMPABLE=0
6. enforce                           # Landlock restrict_self() + seccomp filters
   # seccomp install order: set_no_new_privs → clone3 ENOSYS filter → main EPERM filter

Why the agent has no capabilities

A uid transition from 0 to non-root clears the permitted/effective capability sets, and execve as non-root with PR_SET_NO_NEW_PRIVS cannot regain them. CAP_SYS_ADMIN is gone as a consequence of the uid change; mount is additionally denied by seccomp as defense in depth. Supervisor-only env vars are stripped from the child (SUPERVISOR_ONLY_ENV_VARS).

Supervisor self-hardening

apply_supervisor_prelude installs a seccomp filter on the supervisor itself after privileged bootstrap, blocking mount, bpf, perf_event_open, userfaultfd, setns, ptrace, etc. — a compromised supervisor loses the ability to re-mount or re-enter namespaces even though the drivers granted it the caps (§17). The agent-to-supervisor boundary is: uid separation + seccomp + ptrace block + PR_SET_DUMPABLE=0.

05

The four policy domains

D0003NVIDIA official

Four independent domains form a defense-in-depth stack. The lower two are kernel-level and locked at creation; the upper two are proxy-level and hot-reloadable. Policies are authored in YAML and compiled to OPA/Rego, evaluated for each outbound request.

Filesystem STATIC · locked at creation

Mechanism: the Linux Landlock security module (LSM), applied via syscall 444 (landlock_create_ruleset), implemented in openshell-supervisor-process/src/sandbox/linux/landlock.rs. ABI detection probes the syscall with a version-check flag and lands in one of five availability states: Available, NotImplemented (ENOSYS), NotEnabled (EOPNOTSUPP), Blocked (EPERM), Unknown.

# SandboxPolicy.filesystem + SandboxPolicy.landlock
filesystem:
  include_workdir: true       # auto-include CWD as read-write
  read_only:
    - /usr
    - /lib
    - /proc
    - /dev/urandom
    - /app
    - /etc
    - /var/log
  read_write:
    - /sandbox
    - /tmp
    - /dev/null

landlock:
  compatibility: best_effort  # or "hard_requirement"

best_effort DEFAULT · FAIL-OPEN

If the kernel lacks Landlock (or restrict_self fails), the sandbox runs with NO filesystem restriction at all. The only signal is a High-severity OCSF DetectionFinding with id landlock-unavailable and a message spelling out that the sandbox “will run WITHOUT filesystem restrictions”. This is a silent downgrade, not graceful degradation.

hard_requirement

Sandbox start fails if Landlock cannot be enforced. Code-evidence recommendation for AIDR: treat landlock-unavailable as a P1 alert and require hard_requirement in every production policy template.

Two-phase design Code evidence: prepare runs as root before drop_privileges — it opens a PathFd for each policy path (so mode-700 directories stay reachable) and builds PathBeneath rules (read_only → access_read, read_write → access_all) under a ruleset that handle_access(access_all), so anything unlisted is denied. enforce runs after drop_privileges via restrict_self() — irrevocable and inherited by children. An empty ruleset is REFUSED (“Refusing to apply an empty ruleset that would block all filesystem access”) — that guard prevents a bricked sandbox, not an open one.

What it prevents: file reads/writes outside the allowlisted paths — an agent cannot read /etc/shadow, write to /usr/bin, or reach arbitrary host directories.

Version note from verified docs Docs verified

Two version facts must be read together. (a) Docs: newer docs (v0.1.2 / v0.1.3 support matrix) mark Landlock as Required, ABI 3+ (Linux 6.2+); older kernels (e.g. RHEL 9.x / RHCOS on kernel < 5.19) may fall into a reduced legacy read-only mode. (b) Code: the inspected commit (f23c2c8, 2026-06-18) builds its ruleset with AccessFs::from_all(ABI::V2) — ABI V2, which has no Landlock network rules — and its default best_effort mode runs unrestricted when Landlock is unavailable (see above), which is NOT fail-closed. The commit predates the checked docs and versions drift: pin your version, and verify both the ABI level and the compatibility default in the tree you deploy.

Process STATIC · locked at creation

Mechanism Code evidence: a seccomp-BPF DENY-LIST on top of a uid drop — not an allow-list, and not a capset drop. compile_filter is built with Errno(EPERM): matched syscalls return EPERM, everything else is allowed. That is a deliberate compatibility tradeoff — any syscall not on the list, including future ones, is reachable. Policy validation still rejects any process identity other than sandbox:sandbox (InvalidProcessIdentity).

# SandboxPolicy.process
process:
  run_as_user: sandbox
  run_as_group: sandbox
  • The agent runs as sandbox:sandbox — never root. Capabilities are lost as a consequence of setuid(non-root) + execve + PR_SET_NO_NEW_PRIVS — there is no explicit capset / bounding-set drop in the supervisor (§3).
  • Blocked unconditionally: memfd_create, ptrace, bpf, process_vm_readv/writev, pidfd_*, io_uring_setup, mount, the new mount-API syscalls (fsopen / fsconfig / fsmount / fspick / move_mount / open_tree — they bypass the SYS_mount block entirely), setns, umount2, pivot_root, userfaultfd, perf_event_open.
  • Socket domains: AF_PACKET, AF_BLUETOOTH, AF_VSOCK blocked; AF_INET / AF_INET6 blocked when network mode is not Proxy/Allow; socket(AF_NETLINK, *, proto != 0) blocked — only NETLINK_ROUTE is allowed.
  • Conditional argument rules: execveat with AT_EMPTY_PATH, unshare / clone with CLONE_NEWUSER, and seccomp(SECCOMP_SET_MODE_FILTER) itself. clone3 cannot be arg-filtered (flags live in a struct), so it gets a separate ENOSYS filter — glibc then falls back to clone, where CLONE_NEWUSER is filtered; EPERM would break glibc.
  • Install order: set_no_new_privs → clone3 filter → main filter. Behavioural tests fork a child, install the filter, and assert EPERM for memfd_create / ptrace / setns.

What it prevents: the escalation primitives — ptrace/process_vm attacks on the supervisor, mount and namespace re-entry, userns creation, fileless exec via memfd, io_uring and bpf surfaces. What it does not prevent: anything not on the deny-list, and any judgement about intent.

Network DYNAMIC · hot-reloadable

Mechanism Corrected · code evidence: there is NO redirect. The agent sits in a network namespace whose only route is the host veth (10.200.0.x/24). generate_bypass_ruleset installs an nftables output chain that accepts traffic to the proxy IP/port and lo, accepts established/related, logs, then REJECTS every other TCP/UDP packet (icmp port-unreachable) — there is no dnat / redirect / tproxy rule anywhere. Traffic reaches the proxy only because child_env sets HTTP_PROXY / HTTPS_PROXY / ALL_PROXY (+ lowercase, grpc_proxy) to http://10.200.0.1:{port}, with NO_PROXY=127.0.0.1,localhost,::1 and NODE_USE_ENV_PROXY=1; tls_env_vars point clients at the sandbox CA. A binary that ignores proxy env vars hits the nft reject, not the proxy; protocols that cannot ride CONNECT (raw UDP, QUIC) are simply unavailable.

Degraded mode is possible here too Code evidence

install_bypass_rules is non-fatal: if nft is missing the sandbox continues “degraded”; if kernel nft_log is unavailable it falls back to a reject-only ruleset. Even then the netns has no route except to the host veth, so direct egress still cannot reach the internet unless the host forwards/NATs the veth subnet — a deployment property, not verified in the code reading (§17).

Who is calling? Process identity with SHA-256 TOFU Code evidence

Before OPA decides, the proxy binds the connection to a process. resolve_process_identity / resolve_owner_identity map the connecting socket's inode to PIDs via /proc, read /proc/<pid>/exe, and verify_or_cache computes a SHA-256 of the binary with trust-on-first-use — a binary replaced on disk after first use is detected. The same check runs for each ancestor, and cmdline_paths are collected. If several PIDs share the socket with different policy identities, the connection is denied as ambiguous. OPA receives NetworkInput{host, port, binary_path, binary_sha256, ancestors, cmdline_paths}.

Rego (sandbox-policy.rego): default allow_network = false and default network_action = "deny"; allow_request requires not deny_request — deny overrides allow. Binary matching deliberately excludes cmdline (argv[0] is spoofable); only /proc/pid/exe and ancestors are trusted. method_matches lets HEAD match a GET rule; path_matches uses glob with “/” as delimiter and assumes canonicalization already ran (below).

SSRF defenses (after OPA allows) Code evidence

  • is_always_blocked_ip — loopback, link-local 169.254.0.0/16 (incl. cloud metadata), unspecified, and IPv4-mapped IPv6 forms are never exemptable.
  • reject_internal_resolved_addrs — RFC1918 / internal resolutions are rejected unless the endpoint declares allowed_ips. This stops DNS-rebinding to 127.0.0.1 or the metadata IP.
  • validate_allowed_ips_for_resolved_addrs — even with allowed_ips, ports in BLOCKED_CONTROL_PLANE_PORTS are rejected, and always-blocked IPs stay rejected.
  • A CIDR overlapping always-blocked ranges (e.g. 0.0.0.0/0) is rejected at policy validation time.

L7 relay flow, canonicalization & TLS MITM Code evidence

# l7/relay.rs relay_rest — per request
parse request
  → secrets::rewrite_target_for_eval   # OPA sees the REDACTED target only
  → evaluate_l7_request                # Rego: allow | audit | deny; stale policy generation → error
  → OCSF HttpActivity
  → forward with SecretResolver        # real secret substituted here, at egress
    or 403 in enforce mode
  • Path canonicalization (l7/path.rs) runs before Rego matching and rejects .., %2e%2e, //, ;params and encoded %2F — so /repos/x/../../admin or /repos/x%2F.. cannot pass a GET /repos/* glob while hitting a different path upstream.
  • TLS MITM: SandboxCa is ephemeral per sandbox (CN “OpenShell Sandbox CA”); a CertCache mints per-host leaf certs; tls_terminate_client faces the agent, tls_connect_upstream uses the real root store. Clients with pinned certs or a custom trust store fail rather than bypass.
  • GraphQL (operation type / name / field, persisted-query registry), WebSocket policy and SQL command rules all feed the same request_denied_for_endpoint decision.

Inference routing DYNAMIC · hot-reloadable

Mechanism Code evidence: a CONNECT inference.local:443 is handled by the supervisor itself BEFORE OPA — no network_policies entry is needed or consulted for it. The request is routed through the privacy router (openshell-router); route config, not the agent, chooses provider and model, and provider bundles group related endpoints (API, streaming, embeddings) under a single provider.

  • Routed paths are allow-listed — default_patterns() limits routing to /v1/chat/completions, /v1/completions, /v1/responses, /v1/embeddings, /v1/messages, /v1/models, /v1/models/*. Other paths do not reach the upstream.
  • Credential stripping — should_strip_request_header drops authorization, x-api-key, host, content-length and hop-by-hop headers from the agent's request — whatever auth the agent sent is discarded.
  • Key injection — prepare_backend_request then injects the route's own key: bearer_auth (route.api_key) or a custom header name.
  • Provider selection — routes to the correct LLM provider based on route config / policy.

What it prevents: agents sending prompts to unauthorized LLM providers, credential exfiltration via prompt content, and shadow AI usage. (The NemoClaw reference stack builds managed inference and routing on top of OpenShell; detailed routing rules such as local-vs-cloud selection are documented there, not in the materials verified for this page.)

Composition & merge

A live policy is composed from three sources: (1) the operator-defined base policy, (2) provider policy layers — each attached provider contributes network rules (e.g. the Anthropic provider adds api.anthropic.com), and (3) approved draft proposals learned from denied requests. Merge operations (PolicyMergeOp): AddNetworkRule, RemoveNetworkEndpoint, RemoveNetworkRule, AddDenyRules / AddAllowRules, RemoveNetworkBinary. Before adding anything, policy_covers_rule() checks semantic coverage so an existing policy that already covers a proposal does not accumulate redundant rules.

Policy learning: draft recommendations

When the OPA proxy denies a request, the denial is aggregated by the supervisor and reported to the Gateway, which builds draft policy chunks — proposed additions that would have allowed the denied traffic. Each chunk tracks hit_count, created_at, decided_at and a validation_result from the prover. The operator can:

Approve Reject Edit Undo Clear

The system also auto-drafts proposals for blocked connections; drafts pass the same checks and review — and the opt-in auto-approval gate from Section 2 applies to them as well.

Credential tension — RESOLVED in v2 (placeholders in env, substitution at egress) Code evidence

V1 presented this as an open tension between D0003's env-var materialisation and NVIDIA's proxy-side substitution framing. The code reading resolves it: both halves describe one mechanism, and D0003 architecture's env-var wording was imprecise. At egress, resolve_placeholder checks expiry and validate_resolved_secret rejects CRLF / NUL (header-injection guard); rewrite_header_value handles direct values, Basic (base64) and Bearer forms; if a reserved marker survives rewriting the request fails closed with UnresolvedPlaceholderError and is not forwarded. OPA and OCSF only ever see the redacted target (rewrite_target_for_eval), and the resolver's Debug is hand-written so values cannot leak via logs. Residual risks to keep: (1) the agent can still USE a key on any destination the policy allows — e.g. an allowed host that echoes request headers; (2) an allowed endpoint the agent controls can receive data the agent has legitimately read; (3) the supervisor process holds real secrets in memory — see the capability grants in §17 for how strong that boundary is.

Isolation is one axis; policy semantics are another

Conceptual comparison (from the verified research): a plain container shares the host kernel, so namespaces/cgroups alone do not make an agent safe — a policy layer is what constrains it. A MicroVM (Firecracker-style, or OpenShell's own VM driver) gives each sandbox its own kernel behind a hypervisor boundary — stronger isolation, at higher management cost. A user-space kernel such as gVisor intercepts syscalls between the two. OpenShell's distinct strength is not raw isolation but policy semantics: per-binary / per-method / per-path rules, credential binding, and formal verification. The two axes compose — OpenShell's policy layer can itself run on its MicroVM driver.

Third-party sandbox latency figures (E2B ≈150–200 ms, Daytona <90 ms, Modal sub-second) come from different vendors and measurement methods and are not ranked here — they are vendor-reported and not comparable head-to-head.

The dual-emit pattern

Security-relevant events are emitted twice: once as the domain event (e.g. an HttpActivityEvent with a deny disposition) and once as a DetectionFindingEvent carrying an ATT&CK framework mapping. The separation is deliberate: OCSF stays SIEM-grade instead of drowning in plumbing noise.

Code-evidence additions: severity rules, log hygiene, bypass monitor Code evidence

  • Severity rules (project AGENTS.md): denied = Medium; Landlock unavailable = High. Every allow/deny decision emits an OCSF v1.7.0 event via NetworkActivityBuilder (L4), HttpActivityBuilder (L7), ProcessActivityBuilder, ConfigStateChangeBuilder (policy/Landlock) and DetectionFindingBuilder (security alerts, dual-emitted).
  • Log hygiene rule (AGENTS.md): never log secrets or query parameters in OCSF messages — the JSONL may ship externally. This is consistent with the credential design: OPA and OCSF only ever see the redacted target (§5).

This is how proxy-ignoring binaries become observable instead of silently failing.

Seven design principles

D0003
P1

Outbound-only connection

The Supervisor connects out to the Gateway, never the reverse. Sandbox compromise cannot pivot to the Gateway.

P2

Static + dynamic split

Kernel-level policies (filesystem, process) lock at creation because they cannot be safely relaxed. Application-level policies (network, inference) hot-reload for operational flexibility.

P3

Restrictive default

True for network, caveated for filesystem Code evidence. Empty network_policies denies all egress, and OPA defaults to deny at L4 and L7. But the filesystem default is compatibility: best_effort — on a kernel without Landlock the sandbox runs with NO filesystem restriction (only a High-severity landlock-unavailable finding). Restrictive-by-default holds only if production templates set hard_requirement.

P4

Credential separation

Real credentials live gateway-side and in supervisor memory only. The agent environment carries placeholders (openshell:resolve:env:KEY); the proxy substitutes the real value at egress, fail-closed, and OPA/OCSF only ever see the redacted target. On inference.local, agent auth headers are stripped outright and the route's key is injected instead.

P5

Formal verification before deployment

The Z3 prover mathematically checks policy correctness before application — pre-deployment prevention, not runtime detection.

P6

Compute-agnostic

One ComputeDriver gRPC contract; the same security model across Docker, Podman, Kubernetes and MicroVM.

P7

OCSF-native logging

Security events in OCSF v1.7.0 from day one; the dual-emit pattern routes findings to both operational and security pipelines.

Limitations & open questions

Docs verifiedUnconfirmed items marked

What to press on before running agents against sensitive internal data. Items are ordered roughly by how directly they weaken the guarantees in Sections 1–15.

1 · Kernel & version dependence

Landlock ABI 3+ (per newer docs; the code-inspected commit f23c2c8 builds with ABI V2 — versions drift, §5), nested seccomp user-notification and task-memory access requirements mean older-kernel distributions (RHEL 9.x class) may downgrade — and under the code's default best_effort mode, a missing Landlock means running unrestricted with only a High-severity finding, not failing closed (§5). macOS runs through a Docker Desktop Linux VM and Windows through WSL 2 (experimental) — neither is a native kernel path. Separately, the platform is moving fast: 0.1.0 at the 2026-09-28 launch, docs already at v0.1.6 when checked on 2026-10-29. Policy semantics, prover scope and the support matrix can all shift between versions — pin a version and re-run policy and log-integrity tests on every upgrade.

2 · Supervisor-as-PID 1 attack surface

The semi-trusted tier is the design's own acknowledged tension: the Supervisor holds Landlock/seccomp privilege and network-namespace control from inside the boundary it polices. The code reading sharpens it: container drivers grant the supervisor SYS_ADMIN, NET_ADMIN, SYS_PTRACE and SYSLOG, and Docker runs it AppArmor-unconfined — so the container boundary is only as strong as the supervisor's correctness. Mitigations in code: apply_supervisor_prelude re-filters the supervisor after bootstrap (no mount/bpf/setns/ptrace), the agent is uid-separated with ptrace blocked and PR_SET_DUMPABLE=0, and the supervisor holds real secrets in memory. A supervisor vulnerability is a boundary vulnerability; the split Mode topologies exist partly to shrink what any one supervisor process must hold.

3 · Policy-authoring burden

Least privilege means enumerating files, hosts, methods, paths, binaries and credentials one by one. Too wide and the sandbox is theatre; too strict and the draft-approval queue becomes the bottleneck. Auto-approval relieves the friction while introducing the opposite risk — a newly public host passing with no prover findings. Treat allowlist pruning as scheduled maintenance, not cleanup.

4 · Supervisor as performance single point

Every egress byte passes through the supervisor and its OPA evaluation. NVIDIA's public performance language is qualitative — “minimal overhead” on Vera, “up to 80% faster sandbox performance” on the platform page — with no published configuration, baseline or third-party data. Vendor-reported Load-test with your own workload: supervisor latency and concurrency, sandbox start time, and the effect of policy hot-reload on running tasks.

5 · Credentials — tension RESOLVED in v2; residual risks remain

The v1 open question is closed by the code reading (§8): the agent env carries placeholders (openshell:resolve:env:KEY), real secrets never leave supervisor memory, substitution happens at egress and fails closed, and OPA/OCSF see only the redacted target. What remains open is narrower: (1) the agent can still USE a valid key on any allowed destination (e.g. a header-echoing host); (2) an allowed endpoint the agent controls can receive data it legitimately read; (3) revocation propagation to already-running sandboxes should still be verified at your pinned version (resolve_placeholder checks expiry at substitution time).

6 · Prover coverage limits

The prover proves properties of modelled permissions — not that the whole application, its dependencies and its deployment config are sound, and not that a logically consistent policy is business-appropriate. Multi-agent composition is ongoing work (official blog). Whether GraphQL / MCP / WebSocket / JSON-RPC rules are modelled is reported “no” by an independent test summary but was not confirmed line-by-line against pinned-version docs in the verification pass — verify before relying on the prover for those protocols.

7 · Sentry: the hardware boundary (short version)

This deep dive is about OpenShell's architecture; Sentry enters only as its hardware boundary. Sentry is a reference system design running on BlueField-4 DPU — an out-of-band watchdog in a trust domain isolated from agent and host software, built on DOCA, able to inspect agent requests/responses, provide attested telemetry, verify agent identity and enforce granular zero-trust policies. Two separations matter:

  • OpenShell software does not require BlueField-4. The official FAQ is explicit: it runs on supported local, on-prem, cloud and Kubernetes infrastructure without it. What requires BlueField-4 is Sentry's hardware-isolated guarantee — monitoring that keeps working even if host or workload is compromised.
  • “Quarantines and stops it in milliseconds”, “up to 20% more agent capacity” (2026-10-21 release) and the Vera performance figures are NVIDIA claims with no published measurement method, load conditions or false-positive rates, and no independent or peer-reviewed verification was found as of late October 2026. Vendor-reported, unverified Sentry's detection logic — how it decides an agent is “out of bounds” — is likewise unpublished. Treat Sentry as a design target, not a measured benchmark.

Also unconfirmed: any x86 / non-NVIDIA-chip Sentry roadmap or pricing (secondary reporting says no date; official texts commit to neither), and NemoClaw GDPR / HIPAA / SOC 2 certification claims, which appear only in secondary marketing roundups, not in the official NemoClaw docs checked. An OCSF log format is not itself SOC 2 / GDPR / HIPAA compliance — log integrity, retention, access control and data minimisation remain the deploying organisation's design work.

8 · Telemetry default & partner-list hygiene

Secondary reporting notes OpenShell collects anonymous telemetry by default, disableable via OPENSHELL_TELEMETRY_ENABLED=false, a Helm setting, or compile-time removal — decide and record this explicitly when handling sensitive data. And when citing ecosystem support, keep the two partner lists separate: the 2026-09-28 launch release names its own set (Anthropic, Cisco, CrowdStrike, SpaceXAI, Salesforce, SAP, …; “over 100 organisations” in aggregate, with verb strengths from deployed to exploring), while Google Cloud and TrendAI appear in the broader 2026-10-21 Reference Architecture release. “Partner” never means “deployed customer” — preserve the original verb strength when quoting.

9 · What the code reading did NOT verify Code evidence
  • Kubernetes driver securityContext / capability set — not reviewed; do not assume Docker/Podman parity (§8).
  • Whether the host forwards/NATs the veth subnet per driver — this decides whether a proxy-ignoring client gets even an unrestricted route; it is a deployment property, not visible in the sandbox code.
  • Non-Linux platforms (macOS / VM driver) — the sandbox/linux code is Linux-only; other platforms were not inspected.
  • Two structural blind spots from the code itself: the seccomp filter is a deny-list (any unlisted or future syscall is reachable), and L7 weakens by configuration — enforcement: audit forwards violations, tls: skip is a blind relay, and endpoints without protocol/rules get L4 only (§5).

Code evidence (D0003 controls)

This section collects the verdicts of the D0003 controls companion — a reading of the OpenShell source tree at commit f23c2c8 (2026-06-18). Paths are relative to OpenShell/crates/; line numbers will drift, function names are the stable anchor. Its question is narrower than §1–16: where exactly in the code is each control enforced, and does the code match the common description? The thesis holds; several mechanisms did not (see the corrections log at the top of this page).

The control-plane layout, in one view
Gateway (openshell-server)  ── gRPC, policy store, provider creds, settings
        │  GetSandboxConfig / settings poll
        ▼
Supervisor (openshell-sandbox → -process / -network)   [root, in container]
   ├─ creates netns + veth + nft bypass (reject) rules
   ├─ starts HTTP CONNECT proxy on host-side veth IP  (OPA + L7 + TLS MITM + SecretResolver)
   ├─ starts inference router (openshell-router)
   └─ spawns agent:  setpgid → setns(netns) → drop_privileges → harden → Landlock + seccomp → exec
                     └── agent runs as unprivileged `sandbox` user

Key point: policy is enforced by a separate privileged process the agent cannot signal, ptrace, or read memory from (uid separation, ptrace/process_vm_* blocked by seccomp, PR_SET_DUMPABLE=0).
