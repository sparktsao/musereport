Core thesis

OMP’s product is not the TUI. It is a coding-agent execution harness: one engine that can be driven from the terminal, SDK, RPC, or ACP.

One-line verdict

For power users willing to manage permissions and complexity, OMP is a rare open-source system that makes the harness observable, replaceable, and experimental. If you need strong sandboxing or enterprise-grade durable orchestration, it is not a turnkey answer.

01

Executive verdict: Pi’s minimalist core, now with batteries included

Oh My Pi (omp) is an open-source terminal coding agent from Can Bölük / Stencil Labs, extended from Mario Zechner’s Pi and released under the MIT License.

60+model providers, including major APIs, coding plans, and local enginesOfficial README
31built-in tools spanning files, LSP, DAP, subagents, and browser functionsOfficial README
~80klines in the native Rust core (official approximation)not independently recounted
33.5kGitHub stars at snapshot; plus 3,582 forks2026-09-27 PDT

What it deliberately solves

  • Use the editing protocol itself to reduce model errors and retries.
  • Put LSP, DAP, AST, shell, and code review on one tool surface.
  • Route different models and roles within one session.
  • Make subagents, memory, rules, and MCP first-class capabilities.

What it does not promise

  • It is not a distributed, multi-tenant agent platform.
  • It is not an OS-level sandbox.
  • Session history is not a transactional durable database.
  • Hashline is not optimal for every model or task.

02

Architecture: TypeScript owns policy; Rust handles the hot paths

The core is a clear split between a policy plane and a native data plane. The upper layer optimizes for changeability and extensibility; the lower layer for speed, cross-platform consistency, and fewer fork/exec calls.

Entry

TUI · SDK · RPC · ACP

Interactive terminal, one-shot mode, Node/TS SDK, NDJSON RPC, and editor embedding.

Policy

Bun / TypeScript

Agent loop, prompts, context builder, tools, provider routing, and extensions.

Native

Rust / N-API

Search, AST, shell, PTY, diff, walker, desktop, audio, and compaction primitives.

Boundaries

Repo · LLM · MCP

Local files and Git, LSP/DAP, cloud and local models, the web, and external tools.

The real difference is not “more tools,” but deeper tool semantics.

For example, rename uses LSP’s workspace/willRenameFiles; DAP can attach lldb, dlv, and debugpy; and GitHub PRs, issues, and subagent results are mapped into file-like URIs, reducing the number of verbs a model must learn.

The path of one turn

user prompt
  → session/context builder reconstructs visible history
  → provider adapter converts it to the model-specific dialect
  → streaming text / tool-call delta
  → approval + extension middleware
  → execution through Rust / OS / LSP / DAP / MCP
  → tool result returns to context
  → session append / branch / compact

OFFICIALLY VERIFIEDThe README confirms 14 LSP operations, 28 DAP operations, and multiple entry points; the project notes trace concrete code paths through policy, runtime, and native layers. This is an architectural synthesis across sources, not a claim that every module is implemented in Rust.

03

Hashline: replace “retype old text” with “reference what you just saw”

This is OMP’s most distinctive design: read returns content anchors; edit references hash anchors; if the file changes, the stale anchor becomes invalid and the write is rejected.

read →
[a.ts#0A3B]
41│ const port = 3000;
42│ start(port);
→
edit →
[a.ts#0A3B]
SWAP 41: const port = 8080;
stale hash? reject.

AUTHOR-REPORTED

  • Grok Code Fast 1: 6.7% → 68.3%.
  • Grok 4 Fast: output tokens −61%.

Read this conservatively: it is a design argument, not a universal leaderboard.

The benchmark was designed and run by the author on synthetic, mechanical bug-fixing tasks and has not been independently reproduced. It supports the claim that editing protocols can materially affect results—not that OMP is better for every model.

04

Context, sessions, and memory: treating conversation as reconstructible state

OMP does more than feed a chat array back to the model. It manages stable prefixes, session branches, tool-output pruning, provider-native compaction, and long-term memory.

Session tree

History has parent/leaf semantics and can branch, rewind, and resume; model changes, thinking level, and compaction can also become replayable state.

A ─ B ─ C ─ D
        └─ X ─ Y   ← leaf

ANALYSISThis preserves and switches among exploratory paths, but local persistence is still not equivalent to a server-grade durable workflow.

Context pipeline

The fixed system/tool prefix stays byte-stable where possible; old tool results can be superseded or pruned; near the context limit, OMP can use provider-native compaction or local summarization.

stable prefix
+ rules / skills / repo context
+ branch-visible history
+ memory hints
+ recent tool results

Compaction is not one button; it is a hierarchy

LayerMethodCost / risk
Lightweight pruningNew reads supersede old reads; empty and stale tool outputs are collapsedRequires strict cache invalidation or token accounting can diverge from content
ShakeRemove large code blocks, XML, or tool resultsMay lose debugging detail; recent content must be protected
Native compactionOpenAI / Anthropic provider-specific compaction with replay payloads preservedPayloads are provider-bound; switching models requires re-summarization
Local summarySplit the window, create rolling summaries, and retain recent turnsSummaries can lose critical constraints; this is not lossless
SnapcompactRender text into a bitmap and carry context through the vision stackHighly model-dependent; may save input while increasing reasoning or output

The right role for memory

Available backends include local, Hindsight, and Mnemopi; retain / recall / reflect / learn form a persistent-memory workflow. The key principle is not “remember more,” but this: memory is heuristic context, not an authoritative source of current repository state. Re-read the current state before any destructive change.

05

Security reality: approval is a decision point, not a containment boundary

OMP has rich in-loop controls: approvals, hooks, TTSR, secret obfuscation, an advisor, and security scans. Its biggest gaps are equally clear: yolo is the default, and there is no built-in OS sandbox.

Highest-priority risk: an approved shell command retains the process’s ambient filesystem, network, and subprocess privileges.

The official documentation explicitly states that the pattern policy is not process or filesystem containment; eval can launch a subprocess, so bash.patterns cannot be treated as comprehensive blocking.

Approval tiers BUILT-IN

Three tiers—read / write / exec—and three modes—always-ask, write, and yolo—with per-tool allow / deny / prompt controls.

TTSR / hooks STRONG IN-LOOP

Can block or rewrite before a tool call, and interrupt, inject, or retry when a streamed output matches a rule.

Extensions TRUST BOUNDARY

TypeScript extensions run in-process with the main program; treat third-party extensions as local software, not low-privilege plugins.

Subagents BLAST RADIUS

Can use isolated worktrees, but headless tool execution and host privileges must still be constrained by parent policy.

Memory / rules POISONABLE

AGENTS files, skills, and memory can all carry stale or malicious content into future sessions.

Audit / history REPLAYABLE

Tree-structured history aids replay and inspection, but local files are not a tamper-evident remote log.

Recommended baseline

  • On shared machines, in automation, or for sensitive repositories, explicitly use always-ask or write; do not accept the default yolo mode.
  • Open untrusted repositories with extensions, skills, and rules disabled, because project-level code and rules are themselves supply-chain entry points.
  • Run inside a container, VM, or OS sandbox; treat approval and containment as separate control planes.
  • Restrict egress, minimize exposed credentials, and pin MCP servers and extensions by version and source.
  • Use worktrees, a clean Git state, targeted tests, and checkpoints so agent errors are recoverable.

Competitive position: not “who has the most features,” but which layer each option carries for you

Putting OMP in the right category matters. It is a complete harness/product, not a general-purpose agent framework, and not a vertically integrated agent tied to one model provider.

OptionPrimary strengthTrade-off versus OMPBest for
Oh My PiMulti-provider support, LSP/DAP, Hashline, subagents, and a modifiable harnessLarge complexity and permission surface; no strong built-in sandboxPower users, agent-platform research, and heterogeneous model environments
PiMinimal, readable, and a small tool surfaceFewer capabilities but less overhead; better cost/speed in one small third-party sampleDevelopers who want to understand or assemble their own harness
Claude CodeModel/product co-design, mature interaction and permission UXDeeper single-model ecosystem; OMP is more open and routableUsers who prefer vertical integration and less configuration
Codex CLIOS sandbox, network controls, and approval policyStronger provider lock-in; OMP has a broader IDE/provider surfaceLocal coding workflows that prioritize security boundaries
AiderGit-first workflow, repository map, multiple edit formats, and low overheadLess debugger and subagent orchestration depthUsers who prefer a simple, predictable patch workflow
LangGraph / Deep AgentsDurable execution, checkpoints, services, and observabilityIt is a construction framework; OMP is an out-of-the-box agentMulti-tenant production workflows and long-running orchestration
Caution from a small third-party sample

In a 30-task test using the same model, Composio reported 20/30 for Pi and 17/30 for OMP; OMP cost about 3.7× more per success and took roughly 2× as long. The sample and model scope are limited, but the result is a useful warning: batteries-included brings token and coordination taxes, so tool count should not be equated with success rate.

07

Should you adopt it? Start with control requirements, not star count

OMP’s value lies in being decomposable, observable, and modifiable. Choosing it also means accepting responsibility for provider differences, version drift, permissions, and context quality.

Adopt it if you need

  • Cloud and local models in the same workflow.
  • Real LSP rename, DAP debugging, and AST edits.
  • Multiple subagents, role routing, and live steering.
  • To study or modify tool schemas, context, memory, and editing protocols.
  • An open-source, MIT-licensed, self-managed harness.

Avoid it for now if you need

  • OS-level sandboxing and egress policy by default.
  • A multi-tenant, distributed, transactionally recoverable durable runtime.
  • A turnkey experience with low cognitive overhead and single-model optimization.
  • A slowly changing enterprise surface and long certification cycles.

Recommended evaluation sequence

  1. Pin the version. Releases move extremely fast; do not track latest in CI or team environments.
  2. Reduce privileges first. Start with always-ask or write mode in sensitive environments.
  3. Test only three differentiators. Hashline editing, LSP rename, and DAP debugging.
  4. Then enable subagents. Use 2–3 genuinely independent work packages to measure CPU, RAM, and token costs.
  5. Evaluate memory and extensions last. Establish trusted sources and an update process before enabling persistence and the plugin ecosystem.
