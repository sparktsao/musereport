AI 工程師能力該怎麼評估？

答案不是「寫了多少 code」，而是能否把 AI 的速度轉成可驗證、可維護、可承擔的工程成果。研究顯示，真正拉開差距的是引導、驗證、架構判斷與範圍控制。

THE SHORT ANSWER

評估一位 AI 工程師，應看「受人類監督後存活的成果」，而不是 prompt 數量、AI 使用率或單次 benchmark 分數。

建議以工程品質作為門檻，再觀察 Steering、Planning、Product Thinking 與 Execution Leverage。所有定量資料都需搭配工作樣本、決策脈絡與人工覆核。

01 / RUBRIC

五軸不是五個 KPI，而是五種可觀察行為

Paxel 的模型與業界方向高度重疊；最有價值的是把 session、commit 與結果串成因果鏈，而不是再做一個活動量 dashboard。

01

Execution Leverage執行槓桿

能否用更少的人類指導與 review 時間，交付可驗證、可存活的成果。LOC/day、commit 密度只應作情境資料，不是績效本身。

verified output / review hour
30–90 day survival
02

Steering動態引導與糾偏

能否辨識 agent 偏航、建立正確約束、在適當時間介入，並以高品質修正取代反覆「fix it」。

correction quality
context resets
03

Engineering Quality工程品質 · 建議作門檻

架構、邊界條件、測試、安全、回歸與可維護性。AI 產出再快，若 change-failure rate 或 churn 惡化，就不應算作能力提升。

change failure
regression · security
04

Product Thinking產品思維

能否定義問題、裁剪範圍、辨識不該做的事，並清楚解釋正確性與 trade-off，而不是只接受能跑的第一版。

scope pruning
trade-off quality
05

Planning規劃與編排

能否先審查計畫，再讓 agent 執行；把任務拆成可驗證步驟，合理使用 subagent，並維持跨 session 的一致性。

decomposition
episode coherence

不要把五軸加總成一個看似精準的「AI 分數」。工程品質應先達標；其他軸用於解釋能力輪廓與成長方向。個人排名容易造成 surveillance perception、gaming 與文化反彈，研究更支持 team／initiative 層級的應用。

02 / METHODS

真正可量的，是決策如何變成結果

從聊天紀錄或 Git 活動直接推論「能力」風險很高。較可信的做法，是把每個訊號都連回可檢查的 outcome。

M01 · ALIGN

Session ↔ Commit 對齊

把 agent session 的目標、介入點與 Git commit 時序對齊，建立工作 episode；避免把純活動量誤認為產出。

  • 輸入：session event、commit、測試結果
  • 輸出：任務級脈絡，而非單句 prompt
  • 風險：attribution join 多半是機率性
M02 · TRACE

Decision → Outcome Linking

記錄「為什麼選這個設計」，再追到 merge、rollback、bug、review comment 或 30–90 天後的存活狀態。

  • 先看 plan 與替代方案
  • 再看實作、驗證與維運結果
  • 以結果回校判斷品質
M03 · VERIFY

外部驗證覆蓋

agent 自稱「done」不是證據。以測試、lint、安全掃描、observational equivalence 與人工 review 作獨立 gate。

  • 量測通過自動 gate 的比例
  • 記錄 human reviewer 的拒絕原因
  • grader 與產生者必須分離
M04 · LEARN

學習斜率與複利資產

不只看當下表現，也看工程師是否把錯誤轉成 rule、eval、template、skill 或可重用工具，讓後續工作更穩定。

  • 重複錯誤是否下降
  • 是否建立可重用驗證資產
  • 是否能說明捨棄過什麼、為什麼
03 / BENCHMARKS

Benchmark 測 agent 能不能做，不等於工程師會不會做

單次 pass rate 看不到 steering、decomposition、review quality 或 maintainability。以下是可用範圍與主要限制。

RETIREDSWE-bench Verified59.4% audited defects+

可測什麼

固定 harness 下，agent 是否能針對 issue 產生通過 grader 的 patch。

不能代表什麼

OpenAI 於 2026-02-23 停止報分；稽核發現廣泛題目／測試缺陷與模型 contamination。不可用來比較人的工程判斷。

JOB-LIKESWE-Lancer1,400+ tasks · $1M+

可測什麼

真實 freelance 任務、隱藏 end-to-end tests，以及 managerial proposal selection；是目前最接近工作情境的 benchmark 之一。

不能代表什麼

集中於單一 repo、偏 bug-work，且由 OpenAI 建立並評測自家模型。最佳受測模型通過 26.2%，不是人類能力刻度。

ENVIRONMENTTerminal-Benchstate-based checks+

可測什麼

在 containerized terminal 中完成較長流程，並用最終 state 驗證。

不能代表什麼

沒有 private test set；論文本身承認理論上可能透過網路讀到 oracle solution。仍無法直接觀察人的監督品質。

END-TO-ENDτ^τ-bench23.9% vs expert 82.2%+

可測什麼

不能代表什麼

依賴 simulator 與 judge；外部稽核曾發現 reward 與實際結果不一致。需防 reward hacking 與 judge bias。

04 / HIRING

AI-enabled 面試的訊號：看候選人怎麼懷疑 AI

2025–2026 的公開做法逐漸把 AI 帶進面試，但業界仍分裂。共同點不是速度，而是 error-catching、trade-off explanation 與 decomposition。

值得觀察的正向訊號

Karat NextGen、Zapier AI Fluency v2、Canva 與 Datadog 的公開或第三方整理，都指向同一組能力。

能抓出並修正 AI 的錯誤不只知道答案錯，也能定位 assumption 或 test gap。
能解釋 trade-off 與正確性每個重要 AI-generated 部分都能自己說明與承擔。
先拆問題，再選工具不把複雜需求整包丟給 agent。
能描述學習斜率用過什麼、放棄什麼、為什麼改變 workflow。

容易誤判的負向訊號

這些訊號可觸發追問，但不可自動判定能力或不誠實；尤其情緒與短 prompt 受任務情境影響很大。

AI 使用量或 suggestion acceptance接受不代表 merge，更不代表 30–90 天後仍存活。
LOC、commit、PR 數量可能同時伴隨 rework、churn 與 review bottleneck。
單次 benchmark 高分可能受 harness、contamination 與 grader defect 影響。
短 prompt 或挫折語句只能作 investigation cue，不是能力或人格結論。
05 / TRUST

先證明不會洩漏，再談全面蒐集

Paxel 的 local-first、redacted-summary、fail-closed 方向符合業界常見模式；但「零洩漏」不應被當作絕對保證，redaction 本身仍有漏網風險。

01 · LOCAL

本地擷取

repo 唯讀、原始碼與完整對話不離開裝置。

02 · REDACT

脫敏與最小化

regex、NER、custom recognizer；保留一致 placeholder。

03 · GATE

Fail-closed 邊界

無法確認安全的資料不送出；預覽與輸出共用規則。

04 · AGGREGATE

聚合＋人工覆核

只呈現必要統計與證據；敏感 verdict 不自動化。

進階選項：研究顯示 differential privacy 可降低 membership-inference 風險；一篇 2026 論文報告 AUC 由 0.901 降至 0.606，但其效用成本與適用範圍仍需依場景驗證。閱讀論文 ↗

Anti-gaming：可以採用

產生者與 evaluator 分離外部、對抗式評估；不要接受 agent 自己宣告成功。
Judge blinding 與 abstention對低信心案例拒判，定期與人類校準。
流程訊號觸發人工 review異常編輯軌跡、無中間狀態等不可直接自動拒絕。

仍未核實的主張

HMAC nonce 能「數學上封死」刷分本次未找到公開實作或獨立證據；provenance 不等於判斷正確。
「Fail-closed developer analytics」是成熟標準安全概念存在，但未找到此場景的 canonical reference。
Paxel／YC script 的公開存在性五軸來自提供材料，本次未取得可獨立驗證的公開來源。
RECOMMENDED EVALUATION DESIGN

把評估設計成「證據檔案」，不是員工排行榜

每個 episode 保留問題定義、計畫、關鍵介入、驗證、review 與後續結果。先由工程品質 gate 擋下不可接受的產出，再用其餘四軸描述優勢與改進方向。對人做 consequential decision 時，必須提供情境、申訴與人工覆核。

Outcome first存活、失敗、回歸、review burden
Process evidenceplan、steering、verification trace
Human judgmenttrade-off、context、appeal
Team-level by default避免 surveillance 與 gaming
