How OMP
Actually Works

A code-path-first report on the architecture, orchestration loop, stop conditions, tool and skill loading, context reconstruction, memory, compaction, retrieval, and prompt composition.

Research scopeEnglish by default · technical deep dive
Based on 15 supplied code-study notes plus official public documentation
Snapshot: 2026-09-27/28 PDT; fast-moving codebase
The default view is the full code-path analysis.
Working mental model

OMP is a replayable agent runtime, not just a chat loop: discovery builds capabilities, the session projects one branch of history, the runtime alternates model calls and tool batches, and persistence records every state transition needed to resume.

What matters most

The model decides what to retrieve, which tools to call, and when it is done. OMP supplies the control plane: schemas, approvals, interrupts, persistence, pruning, compaction, and provider adaptation.

00

The whole system in one page

Read this left to right. The CLI is the product shell; the agent package is the reusable state machine; the AI package is the provider boundary; Rust accelerates hot paths.

Discover

Rules · skills · MCP · context files

Provider-priority merge creates a deduplicated capability feed.

Compose

Session + prompts

Build system blocks, project context, one leaf-path, tools, and memory hints.

Run

Model ⇄ tools

Stream output, execute runnable calls, append results, then re-sample.

Persist

JSONL tree

Append messages and state events; compact only the model projection.

History ≠ context.

The JSONL session is the full append-only event tree. The model receives a sanitized projection of the current root-to-leaf branch, often a compaction summary plus a recent verbatim tail.

Capability discovery

Project and user sources—OMP, Claude, Codex, Gemini, Cursor, Windsurf, Cline, GitHub, VS Code, MCP—are loaded with explicit priorities. First provider to claim a capability name wins. Separate feeds exist for context files, rules, skills, tools, and extensions.

Session wiring

createAgentSession() constructs one AgentSession, injecting settings, TTSR buckets, tool session services, built-ins, MCP, memory, advisor, and the final message-to-provider conversion chain.

Architectural consequence

The same loop can be driven headlessly or interactively because rendering is an event consumer. Likewise, provider differences are isolated at the last mile rather than leaking into every tool and session module.

02

Major agent loop and stop conditions

The loop is provider-agnostic and model-driven. OMP does not run a separate “sufficiency” algorithm; a turn continues when runnable tool calls or queued messages exist.

The actual control flow

AgentSession.prompt()
  ├─ validate model / credentials / usage
  ├─ optional pre-prompt compaction
  ├─ build system prompt + leaf-path context
  └─ Agent.prompt() → agentLoop()

OUTER LOOP
  collect steering / asides / follow-ups
  INNER LOOP while tool calls or pending messages exist
    1. deadline + pause gate
    2. fold pending messages into context
    3. prepareProviderCall()
       convertToLlm → normalize messages/tools → provider transform
    4. beforeModelCall gate
    5. streamAssistantResponse()
       text / thinking / tool-call deltas → AgentEvent stream
    6. if runnable tool calls: executeToolCalls()
       validate → approve → hooks → execute → normalize result
    7. append assistant + tool results; emit turn_end
  if late queued work exists: continue OUTER LOOP
  else: emit agent_end
What decides “answer now” versus “use a tool”?

The model. The provider stream may contain prose, thinking, tool calls, or a mix. After the stream settles, OMP inspects the final message. Runnable tool calls continue the loop; text-only completion with no queued work terminates naturally.

Runnable-call rule

Final messageRunnable?Loop behavior
Text only, stopReason="stop"NoNatural completion, unless a steering/follow-up message is waiting.
Tool calls with "toolUse"YesExecute the tool batch, append results, call the model again.
Tool calls with "stop"YesAlso execute; this handles providers that emit calls under an end-turn status.
"length"NoDo not trust possibly truncated arguments; synthesize skipped results.
"error" or "aborted"NoCreate placeholder results for orphaned calls and end the run.

Eight termination paths

1 · Natural completion NORMAL

No runnable tool calls and no steering, aside, or follow-up messages remain.

2 · Deadline HARD STOP

Checked at multiple action boundaries; pending calls receive aborted synthetic results.

3 · Host gate PRE-CALL

beforeModelCall returns {stop:true}; no provider request is sent.

4 · Provider error/abort HARD EXIT

The settled assistant message has error or aborted stop reason.

5 · External AbortSignal USER/HOST

User interrupt races the stream iterator; the runtime drains and synthesizes an aborted assistant turn.

6 · Terminal tool yield GRACEFUL

A special abort symbol ends a subagent after its final typed yield; completed results are preserved.

7 · Guard exhaustion FAIL

Three ignored soft-tool escalations or repeated Harmony-protocol leakage fail the stream to avoid infinite loops.

8 · Paused-turn cap BOUNDED

Provider pause continuations are bounded (eight in the studied snapshot).

Steering is not follow-up

Steer injects a message at the next step boundary and can interrupt tools marked interruptible. Follow-up waits until the current turn would otherwise finish. Aside enters at a boundary without canceling the current batch.

Failure is data

Tool validation failures, missing tools, thrown exceptions, blocked calls, and infrastructure skips become toolResult messages with error details. A single tool failure normally does not crash the entire turn; the model receives the failure and decides what to do next.

No hidden “I have enough information” oracle

Retrieval sufficiency is emergent: the model stops calling tools and emits a final response. OMP bounds pathological cases, but it does not calculate semantic completeness or confidence.

03

Tools, skills, MCP, and capability flood control

Tools are executable typed capabilities. Skills are reusable instruction bundles. OMP keeps those concepts separate, then uses discovery and virtual URI schemes to avoid dumping every schema into every request.

Tool contract

ToolDefinition / AgentTool
  name, label, description, parameters
  approval: read | write | exec
  loadMode: essential | discoverable
  execution: execute(args, signal, onUpdate, context)
  optional: concurrency, speculation, interruptible, deferrable,
            renderCall/renderResult, matcher snapshots for TTSR

Built-in tool families

  • Files/search: read, write, Hashline edit, AST edit, glob, grep, AST grep
  • Execution: persistent shell, Python/JS eval
  • Code intelligence: LSP, DAP debugger, security scan
  • Coordination: task, hub, todo, ask, yield
  • Memory: retain, recall, reflect, learn, manage skill
  • External: web search, browser/computer, GitHub, MCP

Execution pipeline

  1. Resolve canonical tool name.
  2. Validate arguments against schema.
  3. Resolve approval tier and per-tool override.
  4. Run beforeToolCall hooks.
  5. Execute with interrupt/cancellation signals.
  6. Coerce output into valid content blocks.
  7. Run afterToolCall; append result.

Essential versus discoverable

A small core stays in the provider’s top-level tool schema. Most specialized tools—including MCP and extension tools—can be mounted under xd://. The model reads xd:// to list devices, reads xd://<tool> for documentation/schema, then writes JSON arguments to that URI to execute.

read  xd://             → catalog of mounted tools
read  xd://ast-grep     → docs + argument schema
write xd://ast-grep     → execute with JSON body

The studied snapshot budgets inline xdev docs at 48,000 characters, caps each device at 10,000 characters, and caps external MCP/custom summaries at 200 bytes. When xdev already documents tools in the system prompt, wire-level tool descriptions can be stripped to avoid duplication.

Skills: discovery, listing, and injection

StageMechanismWhy it matters
Definition<skill>/SKILL.md with YAML name, description, optional globs, alwaysApply, hideContent can remain external until a task actually needs it.
DiscoveryProject/user OMP, Claude, Codex, plugin, custom, and managed-skill sources merge by priorityAuthored project behavior overrides auto-learned behavior.

Skill ≠ tool.

A skill changes instructions and may point at scripts/assets; it is not itself an executable capability unless paired with tools. A tool exposes an action schema and side effects; its prompt description teaches the model when and how to call it.

MCP bridge

MCP servers are discovered, connected, and asked for tools/list. OMP sanitizes and namespaces names, caps them to provider limits, deduplicates collisions deterministically, strips its internal intent field before outbound calls, converts MCP content blocks back into agent content, and performs one auth or reconnect retry where appropriate. MCP tools are discoverable and write-tier by default in the code-study snapshot.

Context-growth controls around tools

  • xdev mounting: removes discoverable schemas from the wire tool list.
  • Schema-description pruning: avoids sending descriptions twice.
  • Supersede pruning: older reads of the same path collapse.
  • Shake: replaces large historical tool outputs with placeholders while protecting recent context and skill payloads.
  • Roster notices: mid-session tool changes are announced so the model does not act on a stale catalog.
04

Context, session memory, long-term memory, and compaction

There are three different things often called “memory”: the session journal, the live model context, and optional cross-session memory backends. Keeping them separate explains most of OMP’s behavior.

Disk history

SessionEntry[]

Complete append-only JSONL tree: messages plus model, mode, compaction, rule, label, and credential-pin events.

Runtime projection

AgentMessage[]

One root-to-leaf branch with reset/compaction boundaries and unsafe partial turns removed.

Provider request

Context

System blocks, normalized tool schemas, and provider-wire messages after dialect transforms.

Session reconstruction

locate current leaf
  → walk parentId links to root (cycle-guarded)
  → replay latest model / thinking / tier / mode / TTSR state
  → choose reset or latest compaction boundary
  → emit summary + kept tail, or entire branch
  → convert entries to AgentMessage[]
  → strip dangling tool calls and unsafe signed reasoning
  → convertToLlm() + secret obfuscation + provider transform
Branching does not delete.

/tree moves the current leaf in the same journal. /branch materializes a new resumable session. /undo can attach a branch summary. /clear appends a reset boundary; the old path remains exportable.

Prompt-cache stability

The AppendOnlyContextManager freezes a stable prefix of system blocks and tools, then appends messages. It fingerprints the prefix and hashes message content to find the longest unchanged byte prefix. After pruning or compaction, explicit cache invalidation prevents stale token and digest estimates. Date/cwd reminders can live in the first user turn rather than the system prompt so subsequent requests retain a stable prefix.

Token accounting

Instead of re-tokenizing the full transcript every turn, OMP finds the newest settled assistant message with valid provider usage and treats that as an accounting anchor. It only estimates the unaccounted tail. Trigger logic uses the larger of provider-reported usage and a local estimate so on-wire compression cannot hide a nearly full context.

Compaction ladder

StageWhat it doesWhat can be lost / constrained
SupersedeOlder reads of the same path become short markers; uneventful results can be elided.Old evidence disappears from live context, though history remains on disk.
Age pruningBeyond a protected recent token tail, large tool outputs are truncated only when savings justify cache churn.Detailed logs and outputs; protected skill payloads are exempt.
ShakeSurgically replaces large tool bodies, fenced code, or top-level XML blocks.Debug detail; conservative, aggressive, and rescue profiles trade retention for space.
Provider-nativeOpenAI/Anthropic compaction stores opaque replacement or encrypted replay payloads.Payloads are provider-bound; a model/provider switch may force local re-summarization.

Automatic compaction triggers when usage exceeds contextWindow − max(15% of window, reserveTokens); the studied default floor for reserve was 16,384 tokens. Local summarization keeps a recent tail (20,000 tokens in the study snapshot), never cuts at an orphan tool result, and can halve windows on provider overflow.

Cross-session memory

Backends

The studied code supports off/local plus optional Hindsight, Mnemopi, and Sharpshooter-style pipelines. Official README currently describes local, Hindsight, and Mnemopi. Exact backend names are version-sensitive.

Lifecycle

retain records facts, recall retrieves, reflect/learn extract reusable lessons, and consolidation can update summaries and managed skills for future sessions.

Correctness rule

Memory is heuristic guidance, never authoritative repository state. Re-read the current file, branch, issue, or external source before acting on a remembered fact.

05

Retrieval from files, memory, the web, and virtual filesystems

OMP does not have one global RAG engine. Retrieval is a family of channels with different ranking semantics, all chosen by the model.

ChannelQuery generationRankingHard limits in study snapshot
globModel supplies path patternsModification time, newest first200 paths; ~5 s timeout
grepModel writes regex directly; Rust regex with PCRE2 fallbackNo relevance score; round-robin across matching files20 files by default, 2,000 internal matches, 4 MB/file, ~30 s
AST grepModel writes a structural tree-sitter patternDeterministic path + line order50 matches by default
readDirect path or internal URINoneSelector/range-dependent
Mnemopi memoryNatural-language query embedded locally or remotelyFour retrieval voices → RRF fusion → MMR diversity rerankTop-k/config-dependent
Web searchModel text plus parsed site/date/title/filetype directivesProvider-dependent; constraints are leniently post-filteredBackend-dependent
File retrieval is not embedding RAG.

Repository search is lexical or structural. No central keyword extractor, semantic index, or cross-tool relevance score sits in front of grep/glob/read. The model generates patterns, inspects results, and iterates.

A typical file-retrieval sequence

glob("packages/**")                 # orient by path/recency
  → read("xd://")                   # discover specialized search tools
  → grep("prepareProviderCall", …)  # lexical symbol/string search
  → ast-grep("function $NAME…")     # structural search when syntax matters
  → read(candidate paths/ranges)     # inspect primary evidence
  → lsp(definition/references)       # authoritative symbol navigation
  → stop when the model judges the evidence sufficient

Memory retrieval is the exception

Mnemopi is a real retrieval pipeline. A query is embedded, then parallel vector, graph, fact, and temporal “voices” retrieve candidates. Reciprocal Rank Fusion combines their ranks; MMR then balances relevance against redundancy. The studied defaults were RRF_K=60, MMR λ=0.7, and topK=10. This is optional and applies to memory—not repository files.

query
  → embedding
  → [vector | graph | fact | temporal]
  → reciprocal-rank fusion: Σ 1 / (60 + rank)
  → MMR: 0.7 × relevance − 0.3 × similarity-to-selected
  → ranked memories

Web retrieval

The model composes a query. OMP parses Google-style directives such as site:, after:, before:, intitle:, and filetype:, adapts syntax for the selected backend, then post-filters results. If one constraint dimension would remove every result, it is relaxed rather than forcing an empty set.

The public README currently says web search chains 23 providers and passes discovered URLs to read, which can convert web pages and PDFs into structured Markdown. A supplied code-study note counted 27+ provider implementations. Treat the exact count as version-sensitive; the architecture is the stable point.

One filesystem-shaped interface

read/grep/write can address virtual schemes such as pr://, issue://, agent://, skill://, ssh://, artifact://, conflict://, and xd://. This reduces schema entropy: the model reuses file operations instead of learning a new tool per integration.

Retrieval weakness

Because repository search is best-effort and model-driven, it can miss stale files, results beyond caps, semantically related code with different words, or pages a web backend ranks poorly. There is no global recall guarantee.

Prompt templates and composition

Prompts are not one giant string. OMP composes Handlebars templates by role, feature, mode, and tool surface, then preserves stable segments for provider caching.

    APPEND_SYSTEM.md

  prepend plan/goal/vibe context where active
  append leaf-visible session messages
  add volatile date/cwd reminder outside stable system prefix
  normalize tools and provider dialect

High-value template families

system/system-prompt.md

Defines the gather → plan → execute → verify → commit → respond discipline and top-level behavioral contract.

system/plan-mode-active.md

Makes the main agent read-only, turns the plan into an executable spec, and routes approval through the plan surface.

system/orchestrate-notice.md

Requires complete subagent briefs and verification of produced artifacts rather than trusting summaries.

tools/*.md

Per-tool behavioral policy: LSP before cross-file rename, dedicated tools before shell equivalents, schema and safety guidance.

agents/*.md

Specialized reviewer, scout, security, and generic worker roles with bounded scope and output formats.

memories/*.md

Extraction, friction-based admission, consolidation, and read-path guidance for cross-session memory.

steering/*.md

How mid-turn user interjections and parent-agent messages are represented and acknowledged.

security/*.md

Coordinates scan requests, validation, and findings rather than adding one undifferentiated security paragraph.

Customization hierarchy

SYSTEM.md or --system-prompt replaces the default root template; APPEND_SYSTEM.md or --append-system-prompt extends it; TITLE_SYSTEM.md affects automatic session titles only. Internal {{variable}} placeholders are template inputs; user text is treated as plain text rather than recursively compiled.

Prompt engineering here is architecture.

Tool descriptions, mode prompts, memory prompts, and rules are activated at different times. The design goal is to place instructions at the cheapest reliable layer: stable system prefix, on-demand skill, per-tool description, or stream-time interrupt.

07

Rules and Time-Traveling Stream Rules

Rules are bucketed by delivery cost. Always-apply rules spend tokens every turn; rulebook entries are retrieved on demand; TTSR rules stay dormant until streamed output matches.

Always apply

Prompt-time

Full rule body enters the request before generation.

Rulebook

On demand

Name/description is listed; body resolves through rule://.

TTSR

Stream-time

Regex or AST condition watches deltas and injects only on a match.

model stream delta
  → TTSR coordinator checks text / thinking / tool-argument scope
  → regex or in-memory AST match
  → abort current stream
  → append <system-interrupt reason="rule_violation">
  → retry with preserve/discard context policy

non-interrupting tool match
  → fold <system-reminder> into tool result
  → continue loop

TTSR injection bookkeeping is persisted as session entries so a resumed or compacted session remembers which rules fired and can enforce repeat-gap policy. AST rules operate only when the tool exposes a reconstructible source snapshot and a usable file extension.

Why this is distinctive

It trades permanent prompt tax for reactive enforcement. The trade-off is complexity: regex/AST match quality, abort/retry semantics, and repeated-injection state become part of correctness.

08

Subagents, speculative execution, hooks, and extensions

OMP has multiple coordination layers: typed worker tasks, an independent advisor, in-loop hooks, full-trust extensions, and speculative read execution.

MechanismIsolation / contractReturn path
task subagentFresh AgentSession; optional COW/reflink/overlay workspace isolation; explicit task and output schemaTyped yield triggers graceful terminal-tool stop
advisorSeparate model, transcript, context, and budget; observes main-agent deltasSeverity-tagged steering note; main agent may correct or disagree
hookNarrow event API inside the same process; may block/replace selected eventsInjected message, modified args/result, or persisted custom entry
extensionFull in-process API; can register tools, commands, shortcuts, providers, renderersShares normal event/tool/session surfaces

Speculative execution

A per-assistant-message coordinator can start read-only tool candidates before the model commits to them. Candidates form a dependency DAG, run with a bounded in-flight count (two in the studied snapshot), and are reused only when arguments match, resources are unchanged, and host validation passes. Side-effecting work waits for commitment; vetoed parents discard dependents.

Workspace isolation is not process sandboxing

Subagent workspaces can use APFS clones, btrfs/zfs reflinks, overlayfs, projfs, or a copy fallback. That protects file trees and avoids sibling merge collisions. It does not automatically remove ambient network, credential, or subprocess privileges from the executing process.

Trust boundary

Hooks are narrower but still execute local code. Extensions run in-process with broad authority. Treat project-local extensions and plugin packages as software installation, not as harmless prompt text.

09

Security model: policy controls without complete containment

OMP provides rich approval and intervention points, but those controls do not turn the host process into a sandbox.

Approval tiers READ / WRITE / EXEC

Global modes plus per-tool allow/deny/prompt overrides decide whether a call may run.

Pre/post hooks IN-LOOP

Arguments can be rewritten or blocked before execution; results can be rewritten after.

Secret obfuscation TRANSCRIPT

Known secrets are replaced before model/advisor exposure and persisted sessions retain obfuscated forms.

External content UNTRUSTED

Prompt templates warn that pages, tool results, and UI text do not authorize consequential actions.

Project trust GAP

The supplied code study found no project-level trust gate for local OMP extensions/config.

Host privileges GAP

An approved shell or in-process extension inherits what the OMP process can access unless an external sandbox restricts it.

Approval ≠ containment.

An approval dialog answers “may this action run?” It does not constrain what the resulting process, extension, MCP server, or nested shell can reach. For untrusted repositories, use a container/VM/OS sandbox, reduce credentials and egress, disable project-local extensions/rules/skills, and pin versions.

Current official approval documentation states that yolo is the default. Because it auto-approves read, write, and exec tiers, confirm the active configuration explicitly before opening an untrusted repository or running headless automation.
