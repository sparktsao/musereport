OpenShell // Architecture Deep Dive
NVIDIA OpenShell · D0003 architecture notes · checked against NVIDIA sources, 2026-10-29

Kernel-level enforcement for AI agents

OpenShell is a sandbox runtime platform that gives AI coding agents kernel-backed isolation. A Gateway (control plane) manages lifecycle, credentials and policy from outside the sandbox; a Supervisor (data plane) runs inside it and enforces four policy domains — filesystem, process, network and inference routing. The agent is not asked to behave: the kernel denies the syscall.

// The thesis — Layer 0 of the AIDR architecture:
Other layers govern what an agent SHOULD do. OpenShell makes “you CAN'T” real at the OS level — mathematically verified before deployment, enforced by the kernel at runtime.

The three-tier trust model

D0003

Tap a tier to inspect what lives there, what it can do, and what it must never hold. The Supervisor initiates an outbound-only bidirectional gRPC stream to the Gateway (ConnectSupervisor) — the Gateway never connects inward, so sandboxes work behind NAT and firewalls, and a compromised sandbox cannot pivot into the control plane.

▼ creates container / VM · outbound gRPC only · never connects inward ▼
▼ spawns as child · uid=sandbox, gid=sandbox · never root ▼
Reconciliation — “trusted Supervisor” vs “semi-trusted Supervisor”

NVIDIA's blog and docs describe the Supervisor as the trusted side, paired with each sandbox and running outside the agent workload. D0003 refines this into three tiers: the Supervisor runs inside the sandbox boundary as PID 1, so it is semi-trusted — privileged relative to the agent, but not equivalent to the Gateway outside. This page uses the D0003 three-tier model and flags the difference rather than merging the two framings.

Eight responsibilities

1 · Sandbox lifecycle

Create, get, list, delete and watch sandboxes across all compute backends, through the ComputeDriver contract (Section 8).

2 · Credential management

Stores provider credentials gateway-side only; materialises them at sandbox creation and rotates them via OAuth2 / Google SA JWT strategies (Sections 8–9).

3 · Policy management

Stores, composes (base + provider layers + drafts) and distributes policies to supervisors; network policy hot-reloads into running sandboxes.

4 · Authentication

OIDC, Kubernetes ServiceAccount, Cloudflare JWT, gateway-minted sandbox JWT, plus mTLS and SPIFFE workload identity (Section 9).

5 · Supervisor sessions

Maintains the bidirectional ConnectSupervisor stream per sandbox; if the supervisor disconnects, the agent is frozen and only the same supervisor process can reconnect and resume it.

6 · SSH sessions

Issues and revokes SSH sessions; SSH, exec and TCP traffic all relay over the single outbound supervisor stream — there is no inbound path to relay through.

7 · Service exposure

Exposes selected sandbox services externally (ExposeService / GetService / ListServices / DeleteService), under Gateway control rather than sandbox self-publication.

8 · Draft policy learning

Accepts policy analysis from supervisors, builds draft recommendations from aggregated denials, and presents them for operator approve / reject / edit / undo (Section 6).

“The agent cannot approve its own policy change” — with one opt-in exception NVIDIA official

By default, draft proposals stay pending human review and the agent cannot approve its own request. NVIDIA's docs also describe an opt-in auto-approval mode: a proposal may be auto-approved only when the prover delta is empty and there are no security notes. State the guarantee precisely — “manual by default; auto mode remains gated by prover + security notes” — not as an unconditional promise.

Supervisor deep dive

D0003 · openshell-sandbox

The enforcement engine inside the sandbox. It runs as PID 1 (init), spawns the agent as a child process, and makes every policy decision the agent cannot override. The sandbox itself makes no policy decisions of its own — enforcement semantics live here and in the Gateway.

05

The four policy domains

D0003NVIDIA official

Four independent domains form a defense-in-depth stack. The lower two are kernel-level and locked at creation; the upper two are proxy-level and hot-reloadable. Policies are authored in YAML and compiled to OPA/Rego, evaluated for each outbound request.

Filesystem STATIC · locked at creation

Mechanism: the Linux Landlock security module (LSM), applied via syscall 444 (landlock_create_ruleset), implemented in openshell-supervisor-process/src/sandbox/linux/landlock.rs. ABI detection probes the syscall with a version-check flag and lands in one of five availability states: Available, NotImplemented (ENOSYS), NotEnabled (EOPNOTSUPP), Blocked (EPERM), Unknown.

# SandboxPolicy.filesystem + SandboxPolicy.landlock
filesystem:
  include_workdir: true       # auto-include CWD as read-write
  read_only:
    - /usr
    - /lib
    - /proc
    - /dev/urandom
    - /app
    - /etc
    - /var/log
  read_write:
    - /sandbox
    - /tmp
    - /dev/null

landlock:
  compatibility: best_effort  # or "hard_requirement"

best_effort

Apply what the kernel supports; degrade gracefully on older kernels.

hard_requirement

Fail sandbox creation outright if Landlock is unavailable.

What it prevents: file reads/writes outside the allowlisted paths — an agent cannot read /etc/shadow, write to /usr/bin, or reach arbitrary host directories.

Version note from verified docs Docs verified

Newer docs (v0.1.2 / v0.1.3 support matrix) mark Landlock as Required, ABI 3+ (Linux 6.2+), with the baseline not disableable via best_effort. Older kernels (e.g. RHEL 9.x / RHCOS on kernel < 5.19) may fall into a reduced legacy read-only mode, and if Landlock is disabled or seccomp operations are blocked, the sandbox fails closed. D0003's modes and the newer Required stance describe different doc versions — pin your version before relying on either.

Process STATIC · locked at creation

Mechanism: seccomp BPF syscall filtering plus Linux capability dropping. Policy validation rejects any process identity other than sandbox:sandbox (InvalidProcessIdentity).

# SandboxPolicy.process
process:
  run_as_user: sandbox
  run_as_group: sandbox
  • The agent runs as sandbox:sandbox — never root.
  • Dangerous capabilities are dropped (no CAP_NET_ADMIN, no CAP_SYS_ADMIN, …).
  • seccomp BPF blocks dangerous syscalls such as ptrace, mount and reboot.

What it prevents: privilege escalation, container escape via mount-namespace manipulation, and ptrace-based attacks against the supervisor itself.

Network DYNAMIC · hot-reloadable

Mechanism: a three-layer stack. The agent sits in a network namespace where nftables REDIRECT rules force all outbound traffic — DNS included — into the OPA L7 proxy. There is no direct egress path. The proxy terminates or passes through TLS, inspects method / path / query / body, enforces GraphQL operation-level control, and rewrites or injects credentials only for approved endpoints.

# SandboxPolicy.network_policies
network_policies:
  github:
    name: github
    endpoints:
      - host: "api.github.com"
        ports: [443]
        protocol: rest
        tls: terminate
        enforcement: enforce
        access: read-write
        rules:
          - method: GET
            path: "/repos/*"
          - method: POST
            path: "/repos/*/issues"
        deny_rules:
          - method: DELETE
            path: "/repos/*"
    binaries:
      - path: /usr/bin/curl
      - path: /usr/bin/git

Restrictive default: an empty network_policies blocks all network access. What it prevents: unauthorized API calls, DNS-tunneling exfiltration, SSRF, access to link-local metadata services (169.254.x.x), and credential leakage to unapproved endpoints. The supervisor can also inspect HTTP, GraphQL and MCP traffic per the official blog.

Inference routing DYNAMIC · hot-reloadable

Mechanism: DNS interception. The Supervisor intercepts every request to the inference.local hostname and routes it through the privacy router (openshell-router). Agent-supplied credentials are stripped and replaced with gateway-managed ones; the router selects the correct LLM provider under policy, with provider bundles grouping related endpoints (API, streaming, embeddings) under a single provider.

  • Credential stripping — removes agent-supplied credentials, injects gateway-managed credentials.
  • Provider selection — routes to the correct LLM provider based on policy.
  • Privacy routing — requests go to approved providers only.

What it prevents: agents sending prompts to unauthorized LLM providers, credential exfiltration via prompt content, and shadow AI usage. (The NemoClaw reference stack builds managed inference and routing on top of OpenShell; detailed routing rules such as local-vs-cloud selection are documented there, not in the materials verified for this page.)

Policy lifecycle

D0003 · openshell-policy

Why the static/dynamic split exists: kernel policies cannot be safely relaxed after application, so filesystem and process rules lock at creation. Proxy-level policies stay dynamic because an agent may legitimately discover new dependencies — which is exactly what the draft-learning loop is for.

Composition & merge

A live policy is composed from three sources: (1) the operator-defined base policy, (2) provider policy layers — each attached provider contributes network rules (e.g. the Anthropic provider adds api.anthropic.com), and (3) approved draft proposals learned from denied requests. Merge operations (PolicyMergeOp): AddNetworkRule, RemoveNetworkEndpoint, RemoveNetworkRule, AddDenyRules / AddAllowRules, RemoveNetworkBinary. Before adding anything, policy_covers_rule() checks semantic coverage so an existing policy that already covers a proposal does not accumulate redundant rules.

Policy learning: draft recommendations

When the OPA proxy denies a request, the denial is aggregated by the supervisor and reported to the Gateway, which builds draft policy chunks — proposed additions that would have allowed the denied traffic. Each chunk tracks hit_count, created_at, decided_at and a validation_result from the prover. The operator can:

Approve Reject Edit Undo Clear

The system also auto-drafts proposals for blocked connections; drafts pass the same checks and review — and the opt-in auto-approval gate from Section 2 applies to them as well.

The Z3 prover: verification before enforcement

D0003 · openshell-prover

Before a policy is deployed, the prover encodes it as SMT constraints and checks security invariants — credential scope expansion, L7 bypass paths, link-local reachability. This is a pre-enforcement gate: a policy that fails never reaches a sandbox. Per the official blog, the prover checks whether modelled permissions (including provider-contributed access) stay inside the operator-defined boundary, and the agent's own interpretation cannot change the outcome.

The Z3 engine itself, the four finding IDs above, and the exit-code contract come from D0003's repo-level reading (openshell-prover). In the verification pass for this page (2026-10-29), the string “Z3” did not appear in the NVIDIA blog or architecture pages checked — only in third-party repo readings. Treat the Z3 specifics as note/repo-level detail, not as an official NVIDIA blog claim, and verify against the code at your pinned version. Known scope limit: the official blog calls multi-agent composition analysis ongoing work; an independent (non-peer-reviewed) test summary further reports that the boundary check does not model GraphQL / MCP / WebSocket / JSON-RPC rules — flagged here as to-be-confirmed against pinned-version docs.

Why a prover matters: the persuasion experiment NVIDIA describes

NVIDIA's technical blog describes a long-running adversarial exercise in which frontier agents with lowered safeguards spent up to roughly two hours trying to persuade an AI reviewer to grant write access to a protected GitHub repository. OpenShell's formal policy analysis gave the reviewer evidence of the permissions' actual scope even as the agent tried to manipulate it; combined with review and runtime controls, no protected-repository write occurred in the exercise, while useful access remained available.

Vendor-described experiment Quote it as “in NVIDIA's described internal exercise, zero protected writes in that scenario” — the sample size, model names, control group and statistics were not published, so it is not a security guarantee and not proof against persuasion attacks in general.

The key insight in D0003's model: credentials are materialised as environment variables by the Gateway into DriverSandboxSpec.environment — never stored inside the sandbox image. The Supervisor reads them at startup and passes them to the agent process via child_env.

Credential tension — read both mechanisms together

D0003's provisioning model (startup env materialisation → child_env) sits next to NVIDIA's blog framing, which emphasises proxy-side substitution outside the workload: real credentials are replaced at request time, only for endpoints that satisfy both network policy and credential binding, and delivery to an unapproved destination is refused. Both mechanisms are presented here because both are in the sources. The invariant that reconciles them: whatever reaches the agent as env is scoped provider material for approved use; the proxy strips and rewrites agent-originated credentials at request time — and the agent must never see gateway credentials for endpoints it is not approved for. Do not quote either half alone as “credentials never enter the sandbox” or “credentials are just env vars.”

Isolation is one axis; policy semantics are another

Conceptual comparison (from the verified research): a plain container shares the host kernel, so namespaces/cgroups alone do not make an agent safe — a policy layer is what constrains it. A MicroVM (Firecracker-style, or OpenShell's own VM driver) gives each sandbox its own kernel behind a hypervisor boundary — stronger isolation, at higher management cost. A user-space kernel such as gVisor intercepts syscalls between the two. OpenShell's distinct strength is not raw isolation but policy semantics: per-binary / per-method / per-path rules, credential binding, and formal verification. The two axes compose — OpenShell's policy layer can itself run on its MicroVM driver.

Third-party sandbox latency figures (E2B ≈150–200 ms, Daytona <90 ms, Modal sub-second) come from different vendors and measurement methods and are not ranked here — they are vendor-reported and not comparable head-to-head.

Authentication & identity

D0003

A three-variant principal model. The load-bearing invariant: a sandbox principal's sandbox_id must match the sandbox_id in every request body — that single check is what stops a compromised sandbox from addressing another sandbox's resources (IDOR).

enum Principal {
    User(UserPrincipal),        // OIDC-authenticated operator
    Sandbox(SandboxPrincipal),  // supervisor with bound sandbox_id
    Anonymous,                  // health checks, reflection only
}

SandboxPrincipal carries sandbox_id: String (canonical UUID, must match the request body), source: SandboxIdentitySource (how it authenticated), trust_domain: Option<String>.

MethodIdentity sourceUse case
OIDC JWTExternal IdP (Okta, Auth0, …)Operator / user authentication
Gateway-minted JWTSandboxJwtIssuerSandbox bootstrap — the supervisor proving its identity
K8s ServiceAccountPod SA token → IssueSandboxToken RPCK8s-native sandbox bootstrap
Cloudflare JWTCloudflare Access headersZero-trust network overlay
mTLSPer-sandbox client certificateCertificate-based mutual auth (supervisor↔sandbox channel per docs)

Channel security from the verified docs: Gateway JWT for supervisor→gateway (over TLS when enabled), mTLS + sandbox JWT for supervisor→sandbox, with tokens bound to a single sandbox and a single run. The sandbox side holds nothing worth stealing: no gateway signing key, no gateway JWT, no provider credentials in its own right.

Sandbox authentication flow

  1. The Gateway creates the sandbox and mints a sandbox JWT (the token).
  2. The Supervisor starts inside the sandbox holding that token.
  3. It connects back out (ConnectSupervisor) and presents the JWT.
  4. The Gateway validates the JWT and binds the sandbox_id to the session — every later frame inherits that binding.

Each strategy supports audience overrides (ProviderCredentialTokenGrantAudienceOverride) for per-endpoint audience mappings. Operationally: credential rotation and revocation must work without the agent's cooperation — after revocation, verify the supervisor actually refuses the old placeholder.

The dual-emit pattern

Security-relevant events are emitted twice: once as the domain event (e.g. an HttpActivityEvent with a deny disposition) and once as a DetectionFindingEvent carrying an ATT&CK framework mapping. Security findings therefore surface in both operational dashboards and security alert pipelines — neither audience has to mine the other's stream.

What NOT to log as OCSF (project guidance in AGENTS.md, per D0003): OCSF is for observable sandbox behaviour — network decisions, auth, process lifecycle, security findings, config changes. Internal plumbing (gRPC retries, SSH state machines, zombie reaping, denial-flush telemetry) uses plain Rust tracing. The separation is deliberate: OCSF stays SIEM-grade instead of drowning in plumbing noise.

Acceptance-test warning from an independent test Independent test, not peer-reviewed

A single-tester evaluation of v0.1.2 (Sorami, non-peer-reviewed) reported logging gaps on the VM driver — blocked UDP DNS produced no event, the OCSF JSON export did not write to file, and Landlock events appeared only on the VM console. It does not generalise to every deployment, but it belongs on an acceptance checklist: verify that every blocked request actually produces an event, per driver.

The ConnectSupervisor session protocol

The most architecturally significant RPC: it establishes the persistent bidirectional stream between supervisor and gateway (the OpenShell Sandbox Protocol, mutually authenticated over HTTP/2 per the verified docs).

Supervisor → Gateway:  SupervisorHello { sandbox_id, capabilities }
Gateway → Supervisor:  SessionAccepted { session_id }
                       --- or ---
                       SessionRejected { reason }

Ongoing:               SupervisorHeartbeat ↔ GatewayHeartbeat
                       RelayOpen → RelayOpenResult (SSH, exec, TCP channels)
                       RelayClose (either side)

All relay channels — SSH sessions, exec commands, TCP forwarding — are multiplexed over this single stream. The first frame of each relay must be a RelayInit carrying a channel_id; subsequent frames are raw bytes. Walk the full lifecycle in Section 12.

The wider gap list from verified research (beyond the AIDR framing)
  • Model-layer jailbreak (content): guardrails are probabilistic classification; OpenShell is an execution boundary. A model can still emit harmful or false text — it just cannot act on it without authorisation. Pair with NeMo Guardrails + human review; never use OpenShell as a content moderator.
  • Malicious or poisoned model weights: the sandbox does not verify weights; confidential-computing attestation proves environment and firmware, not training-data provenance. Use model signing, SBOM and provenance checks.
  • Insider policy authoring: the prover checks a policy against the operator-defined boundary; if the boundary itself is too wide — or its author can also change the boundary — the proof loses meaning. Auto-approval amplifies this. Separate boundary approval from routine policy changes, require four-eyes, keep tamper-evident change logs.
  • Exfiltration via allowed endpoints: data can still leave through endpoints the policy allows. Policy correctness is a precondition, not an outcome — pair with data classification, DLP, output inspection and periodic allowlist pruning.
  • Side channels: secondary analysis says OpenShell does not address timing / error-message / covert channels; the verification pass found no official guarantee or denial either way — treat as an open question, not a confirmed limitation.
  • Kernel / firmware / host-root compromise (without Sentry): without BlueField-4, host-root compromise can undermine the software boundary. Sentry's continued operation in that scenario is a vendor claim (Section 16).
  • Multi-agent composition: each agent's policy can be individually legal while the combination opens an over-privileged path; the prover's multi-agent check is ongoing work per the official blog.
Vendor-reported defence claims — not verified results Vendor-reported

Claims that the platform “could have prevented” the summer Hugging Face intrusion are vendor inference repeated in secondary reporting, not a retrospective test. Secondary corrections note the incident's causes look closer to test-environment misconfiguration (network left open, some monitoring disabled) than to a novel kernel-escape technique — which cuts both ways: if policy allows the network path, or safeguards are switched off by a human, no sandbox can conjure the missing control. The same status applies to Sentry's millisecond quarantine and the Vera performance figures in Section 16.

Seven design principles

D0003
P1

Outbound-only connection

The Supervisor connects out to the Gateway, never the reverse. Sandbox compromise cannot pivot to the Gateway.

P2

Static + dynamic split

Kernel-level policies (filesystem, process) lock at creation because they cannot be safely relaxed. Application-level policies (network, inference) hot-reload for operational flexibility.

P3

Restrictive default

Empty policies deny everything. No filesystem paths means no access; no network rules means no egress. Policy must explicitly grant.

P4

Credential separation

Credentials are stored gateway-side only, injected at sandbox creation, and agent-originated credentials are stripped and replaced by the proxy.

P5

Formal verification before deployment

The Z3 prover mathematically checks policy correctness before application — pre-deployment prevention, not runtime detection.

P6

Compute-agnostic

One ComputeDriver gRPC contract; the same security model across Docker, Podman, Kubernetes and MicroVM.

P7

OCSF-native logging

Security events in OCSF v1.7.0 from day one; the dual-emit pattern routes findings to both operational and security pipelines.

Limitations & open questions

Docs verifiedUnconfirmed items marked

What to press on before running agents against sensitive internal data. Items are ordered roughly by how directly they weaken the guarantees in Sections 1–15.

1 · Kernel & version dependence

Landlock ABI 3+, nested seccomp user-notification and task-memory access requirements mean older-kernel distributions (RHEL 9.x class) may downgrade or fail closed. macOS runs through a Docker Desktop Linux VM and Windows through WSL 2 (experimental) — neither is a native kernel path. Separately, the platform is moving fast: 0.1.0 at the 2026-09-28 launch, docs already at v0.1.6 when checked on 2026-10-29. Policy semantics, prover scope and the support matrix can all shift between versions — pin a version and re-run policy and log-integrity tests on every upgrade.

2 · Supervisor-as-PID 1 attack surface

The semi-trusted tier is the design's own acknowledged tension: the Supervisor holds Landlock/seccomp privilege and network-namespace control from inside the boundary it polices. seccomp blocks the agent's ptrace/mount paths against it, and the outbound-only model limits blast radius — but a supervisor vulnerability is a boundary vulnerability, and the split Mode topologies exist partly to shrink what any one supervisor process must hold.

3 · Policy-authoring burden

Least privilege means enumerating files, hosts, methods, paths, binaries and credentials one by one. Too wide and the sandbox is theatre; too strict and the draft-approval queue becomes the bottleneck. Auto-approval relieves the friction while introducing the opposite risk — a newly public host passing with no prover findings. Treat allowlist pruning as scheduled maintenance, not cleanup.

4 · Supervisor as performance single point

Every egress byte passes through the supervisor and its OPA evaluation. NVIDIA's public performance language is qualitative — “minimal overhead” on Vera, “up to 80% faster sandbox performance” on the platform page — with no published configuration, baseline or third-party data. Vendor-reported Load-test with your own workload: supervisor latency and concurrency, sandbox start time, and the effect of policy hot-reload on running tasks.

5 · Credential env-vs-proxy tension

See the reconciliation note in Section 8. Open questions for a pinned version: exactly which provider material is materialised into the sandbox environment, what the agent can read from its own env and /proc, and how revocation propagates to already-running sandboxes. These are answerable from the code and docs at your version — they are not answered by marketing copy in either direction.

6 · Prover coverage limits

The prover proves properties of modelled permissions — not that the whole application, its dependencies and its deployment config are sound, and not that a logically consistent policy is business-appropriate. Multi-agent composition is ongoing work (official blog). Whether GraphQL / MCP / WebSocket / JSON-RPC rules are modelled is reported “no” by an independent test summary but was not confirmed line-by-line against pinned-version docs in the verification pass — verify before relying on the prover for those protocols.

7 · Sentry: the hardware boundary (short version)

This deep dive is about OpenShell's architecture; Sentry enters only as its hardware boundary. Sentry is a reference system design running on BlueField-4 DPU — an out-of-band watchdog in a trust domain isolated from agent and host software, built on DOCA, able to inspect agent requests/responses, provide attested telemetry, verify agent identity and enforce granular zero-trust policies. Two separations matter:

  • OpenShell software does not require BlueField-4. The official FAQ is explicit: it runs on supported local, on-prem, cloud and Kubernetes infrastructure without it. What requires BlueField-4 is Sentry's hardware-isolated guarantee — monitoring that keeps working even if host or workload is compromised.
  • “Quarantines and stops it in milliseconds”, “up to 20% more agent capacity” (2026-10-21 release) and the Vera performance figures are NVIDIA claims with no published measurement method, load conditions or false-positive rates, and no independent or peer-reviewed verification was found as of late October 2026. Vendor-reported, unverified Sentry's detection logic — how it decides an agent is “out of bounds” — is likewise unpublished. Treat Sentry as a design target, not a measured benchmark.

Also unconfirmed: any x86 / non-NVIDIA-chip Sentry roadmap or pricing (secondary reporting says no date; official texts commit to neither), and NemoClaw GDPR / HIPAA / SOC 2 certification claims, which appear only in secondary marketing roundups, not in the official NemoClaw docs checked. An OCSF log format is not itself SOC 2 / GDPR / HIPAA compliance — log integrity, retention, access control and data minimisation remain the deploying organisation's design work.

8 · Telemetry default & partner-list hygiene

Secondary reporting notes OpenShell collects anonymous telemetry by default, disableable via OPENSHELL_TELEMETRY_ENABLED=false, a Helm setting, or compile-time removal — decide and record this explicitly when handling sensitive data. And when citing ecosystem support, keep the two partner lists separate: the 2026-09-28 launch release names its own set (Anthropic, Cisco, CrowdStrike, SpaceXAI, Salesforce, SAP, …; “over 100 organisations” in aggregate, with verb strengths from deployed to exploring), while Google Cloud and TrendAI appear in the broader 2026-10-21 Reference Architecture release. “Partner” never means “deployed customer” — preserve the original verb strength when quoting.
